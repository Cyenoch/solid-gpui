# Getting started

One sequence takes a clean external checkout of your own application from install
to a running desktop window: install, prepare, typecheck, develop, test, build, and
preview the production bundle. Advanced integration stays in its own guides and is
linked from each step:

- [Vite integration](vite.md) — the plugin's full option surface, `host: false`, and custom transports.
- [Rust integration](rust-bridge.md) — native modules, desktop hosts, and window configuration.
- [Choose a runtime](runtimes.md) — external Bun, embedded Bun, and QuickJS.
- [Development workflow](hot-reload.md) — watch behavior and reload state contracts.
- [Desktop distribution](distribution.md) — bundles, executables, signing, and target support.

## Prerequisites

- **Bun 1.4.2 or newer.** Vite and the `solid-gpui` tooling run under Bun; start
  Vite with `bun --bun vite`.
- **A Rust toolchain only when the application builds a Rust host.** Install rustup
  with the toolchain in `rust-toolchain.toml`, plus your platform's native build
  dependencies. See [build environment](distribution.md#build-environment).
- **The SDK's Cargo requirements in your workspace root.** Your host crate depends
  on the `solid-gpui` crate from the same pinned checkout (a path or git dependency;
  it is not published to a registry today). Cargo ignores profile
  settings declared by a dependency, so the consuming workspace root must carry the
  `[patch.crates-io]` gpui-pre entries and the debug profiles from this repository's
  `Cargo.toml` (including `rquickjs-sys` for a QuickJS host). `solid-gpui doctor`
  derives the active dependencies, profiles, and patch requirements and reports
  mismatches.

## 1. Install

The SDK is not published to a public registry yet: `@solid-gpui/core` and
`@solid-gpui/vite` do not resolve from npm today, and the `solid-gpui` Rust crate is
consumed from a checkout. Build matching tarballs from one pinned SDK checkout and
install those; do not mix versions from different runs.

In the SDK checkout:

```sh
bun install --frozen-lockfile
bun run task sdk-pack ../sdk-tarballs
```

That writes `solid-gpui-core.tgz`, `solid-gpui-vite.tgz`, `solid-gpui-router.tgz`,
and `solid-gpui-shiki.tgz`, without compiling a native host.

In your application:

```sh
bun init
bun add ../sdk-tarballs/solid-gpui-core.tgz solid-js
bun add -d ../sdk-tarballs/solid-gpui-vite.tgz vite
```

Keep `"type": "module"` in `package.json`. `@solid-gpui/core` is the renderer and
component package; `@solid-gpui/vite` provides the Vite plugin, the `solid-gpui`
CLI, and the test entrypoint. Add `@solid-gpui/router` and `@solid-gpui/shiki` from
the same pack when you need them, and re-run `sdk-pack` plus the install after
pulling a new SDK revision.

When the packages are published to a registry, the same packages install by name and
the rest of this sequence is unchanged; that is not the case today. Debugging SDK
sources directly is a separate, explicit opt-in described in
[source consumption](vite.md#consume-packages-from-source).

## 2. Configure Vite and TypeScript

`vite.config.ts` names the application entry and its native host:

```ts
import { defineConfig } from "vite";
import { solidGpui } from "@solid-gpui/vite";

export default defineConfig({
  plugins: [
    solidGpui({
      entry: "src/app.tsx",
      runtime: "bun",
      native: { manifestPath: "native/Cargo.toml", bin: "my-app" },
    }),
  ],
});
```

`entry` is the module that calls `mountApplication`. `native` builds and watches
that Cargo host and exports its bindings. Use `host: { command }` for an executable
you build yourself, and `host: false` when your own Vite environment and module
runner own the process; both are described in [Vite integration](vite.md).

`runtime` selects the execution model explicitly and is never converted: a bundle
built for `bun` keeps Bun and Node imports, while `runtime: "quickjs"` builds one
self-contained ES module and rejects them. Choose the runtime at build time and run
the result with a matching host.

`tsconfig.json` stays small; the generated project carries the rest:

```json
{
  "extends": "./.solid-gpui/tsconfig.json",
  "compilerOptions": {
    "strict": true,
    "jsx": "preserve",
    "jsxImportSource": "@solid-gpui/core"
  },
  "include": ["src", "vite.config.ts"]
}
```

`.solid-gpui/tsconfig.json` is generated by `prepare` and maps `#native` and
`@solid-gpui/core/components` to the bindings the plugin actually selects, so the
`paths` you would otherwise mirror by hand stay authoritative; it also carries the
resolution mode, `jsx`, and — for a QuickJS runtime — the DOM-free `lib`/`types`
pair, with absolute paths a consumer `baseUrl` cannot break. Your own file adds only
your strictness and `include`. Add `.solid-gpui/` to `.gitignore`.

TypeScript needs `jsx: "preserve"` and `jsxImportSource: "@solid-gpui/core"`; the
latter supplies host element types. The compiler is pinned to
`@solidjs/compiler` 2.0.0-rc.6 while the application runtime remains Solid 1.9.15.

## 3. Prepare native bindings

Add the scripts once, then run the generator after installing (package installation
must never compile a native host, so the script is not named `prepare`):

```json
{
  "scripts": {
    "generate": "solid-gpui prepare",
    "check:generated": "solid-gpui prepare --check",
    "doctor": "solid-gpui doctor",
    "typecheck": "tsc --noEmit",
    "dev": "bun --bun vite",
    "test": "solid-gpui test",
    "build": "bun --bun vite build",
    "preview": "solid-gpui preview"
  }
}
```

```sh
bun run generate
```

`prepare` loads your `vite.config.ts`, builds the configured Cargo host when
needed, runs its `--export-native` entrypoint, and writes:

| Output                       | Contents                                                                                                                                   |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| `.solid-gpui/tsconfig.json`  | Generated TypeScript mappings for the selected bindings. Never hand-edit.                                                                  |
| `.generated/native.ts`       | The host's exported component catalog, commands, and types (`native.output`).                                                              |
| `.solid-gpui/artifacts.json` | The resolved artifact record: `root`, `runtime`, `entry`, `outDir`, bindings, tsconfig, host, and (after a build) the emitted bundle path. |

It does not run the application and does not produce the production bundle.

- `bun run check:generated` (`solid-gpui prepare --check`) writes no files and exits
  non-zero when the bindings or the generated tsconfig are stale or missing. It
  still resolves and builds the host as needed to compare against the real catalog,
  and it does not rewrite `.solid-gpui/artifacts.json`; use it in CI instead of
  relying on a side effect of a dev or build command.
- `bunx solid-gpui prepare --json` prints the resolved artifact record instead of
  prose.
- `bun run doctor` reports environment and dependency problems, including Cargo
  profile and patch mismatches and unsupported runtime or target combinations.

`prepare`, `prepare --check`, `doctor`, `preview`, and `test` accept `--root` and
`--config`. `prepare`/`preview` also accept `--mode` (default `production`), and
`test --mode` defaults to `development`; `doctor` does not support Vite mode
selection. Arguments after `--` are delegated to the preview host or Bun test runner.

## 4. Typecheck

```sh
bunx tsc --noEmit
```

## 5. Develop

```sh
bun --bun vite
```

Vite compiles JSX/TSX and serves modules to the host-owned Bun child; the native
window is managed by the host. Rust sources, Cargo manifests and configuration,
declared build-script inputs, declared native assets, and any `native.watch` paths
queue one host rebuild and session replacement per burst, while application modules
keep normal Vite HMR. `.solid-gpui/`, `target/`, the build output directory, and
`node_modules/` never trigger rebuilds. Captured state, failure recovery, and the
Rust-versus-JavaScript split are in
[managed development sessions](hot-reload.md#managed-development-sessions).

## 6. Test

```sh
bunx solid-gpui test                     # whole suite
bunx solid-gpui test src/app.test.tsx    # one file
```

The command delegates to `runTests({ root?, configFile?, mode?, args? })` from
`@solid-gpui/vite/test`, which loads the same `vite.config.ts` you develop with, so
tests see the real JSX transform, aliases, `?inline` assets, and native bindings
contract instead of a hand-built substitute. It adds the `browser` condition and
dedupes `solid-js` itself, so you never pass `--conditions=browser`, and one
reactive graph is shared with the packaged application. Argument handling is
Bun's: filters and flags are forwarded to `bun test`, so ordinary single-file
invocations work. Import test APIs from `bun:test`.
Tests preserve Bun's real `process.env` and subprocess environment even for a
QuickJS application. Production QuickJS restrictions are unchanged. Pass
`--mode staging` to select mode-dependent Vite configuration during tests.

## 7. Build the bundle

```sh
bun --bun vite build
```

Vite writes one production entry module into your `build.outDir` (default `dist/`):
for Bun it bundles JavaScript dependencies and preserves Bun/Node builtins as
runtime imports; for QuickJS it writes one self-contained ES module and rejects
Bun/Node imports, remaining dynamic imports, and external assets. A build also
prepares the configured native host, normally as an incremental Cargo rebuild, so
`build` and `generate` both keep the host current. The bundle path is recorded in
`.solid-gpui/artifacts.json`, which the build updates with the file it actually
emitted, rather than derived by hand.

This step produces the **bundle** (and the **native executable** when `native` is
configured). It does not package, sign, or produce a **distributable**. See
[Desktop distribution](distribution.md) for that difference and for target support.

## 8. Preview the production bundle

```sh
bun run preview          # solid-gpui preview
```

`preview` runs the already-built host against the bundle recorded in
`.solid-gpui/artifacts.json`: no rebuild, no watcher, and it exits with the host's
status. Pass host arguments after `--`. It fails with the command to run — for
example `vite build`, or `solid-gpui prepare && vite build` — when the record or
the bundle is missing, and it refuses a record whose runtime, bundle, host package,
binary, profile, or target no longer matches the configuration you point it at
(pass `--config` for the configuration the artifacts were built with).
Programmatic callers use `previewApplication({ root?, configFile?, mode?, args?, env? })`
from `@solid-gpui/vite/project`, and scripts that only need locations read the same
record through `prepareProject`/`readNativeArtifacts` from
`@solid-gpui/vite/artifacts` — never `target/<profile>/<bin>` or a hardcoded bundle
path. An application that selects its transport in Rust (for example a
`--production` flag that chooses `EmbeddedTransport` instead of `StdioTransport`)
passes that flag through.
When the config selects an entry or Cargo profile by mode, pass the same `--mode`
to build and preview, such as `vite build --mode release` and
`solid-gpui preview --mode release`.

## Write the application

Solid GPUI's runtime module provides the client Solid primitives and the universal renderer's `createComponent` function.

```ts
import { Pressable, Text, View } from "@solid-gpui/core";
import { createComponent, createSignal } from "@solid-gpui/core/runtime";

export function Counter() {
  const [count, setCount] = createSignal(0);
  return createComponent(View, {
    style: { padding: 24, gap: 12 },
    get children() {
      return [
        createComponent(Text, { children: () => `Count: ${count()}` }),
        createComponent(Pressable, {
          accessibilityRole: "button",
          accessibilityLabel: "Increment",
          onPress: () => setCount((value) => value + 1),
          children: createComponent(Text, { children: "Increment" }),
        }),
      ];
    },
  });
}
```

The getter and function children are reactive reads. When `count` changes, the Solid render effect updates the raw-text Host Node and the root emits one incremental Patch.

The same component in JSX uses the configured plugin and needs no separate setup:

```tsx
import { Pressable, Text, View } from "@solid-gpui/core";
import { createSignal } from "@solid-gpui/core/runtime";

export function Counter() {
  const [count, setCount] = createSignal(0);

  return (
    <View style={{ padding: 24, gap: 12 }}>
      <Text>Count: {count()}</Text>
      <Pressable accessibilityRole="button" onPress={() => setCount((value) => value + 1)}>
        <Text>Increment</Text>
      </Pressable>
    </View>
  );
}
```

Import `For`, `Index`, `Show`, `Switch`, and `Match` from
`@solid-gpui/core/runtime`, not from `solid-js`; the runtime entry supplies native
element types and is the client entry for lifecycle, owner, context, array, and
store helpers (`onMount`, `onCleanup`, `getOwner`, `runWithOwner`, `createContext`,
`useContext`, `splitProps`, `createStore`, and the rest). See
[native control flow](native-composition.md#solid-async-control-flow).

## Mount a root

The configured entry module mounts the application and owns its transport:

```tsx
import { mountApplication } from "@solid-gpui/core";
import { StdioTransport } from "@solid-gpui/core/stdio";
import { Counter } from "./counter";

mountApplication({
  transport: () => new StdioTransport(),
  setup: () => ({ render: () => <Counter /> }),
});
```

The transport factory creates the application-owned connection once and closes it
on final disposal. `StdioTransport` belongs to the process (Bun) runtime and
`EmbeddedTransport` from `@solid-gpui/core/embedded` to embedded Bun and QuickJS;
a custom transport implements the same interface. See
[choose a runtime](runtimes.md) and [Vite integration](vite.md).

Without `mountApplication`, create the root yourself and pass a producer to
`root.render`. This ensures component creation occurs under the root's Solid owner and binds later reactive work to the correct native surface:

```ts
import { createRoot } from "@solid-gpui/core";
import { createComponent } from "@solid-gpui/core/runtime";
import { StdioTransport } from "@solid-gpui/core/stdio";
import { Counter } from "./counter";

const root = createRoot(new StdioTransport(), { surfaceId: 1, epoch: 1 });
root.render(() => createComponent(Counter, {}));
```

## Test without a display

```ts
import { Text, createRoot } from "@solid-gpui/core";
import { TestHost } from "@solid-gpui/core/testing";

const host = new TestHost();
const root = createRoot(host.transport, { surfaceId: 1 });
root.render(() => Text({ children: "ready" }));
console.log(host.surface(1)?.nodes.filter((node) => node.text !== null));
root.unmount();
```

`TestHost` wraps an optional existing `MemoryTransport`, replays Snapshot/Patch
updates and provides node inspection, test events, native DTO props and native-call
replies without private protocol imports. See the [testing interface](vite.md#inspect-renderer-output-without-private-protocol-imports)
for event and reply examples. Use the application's `solid-gpui test` runner;
plain JavaScript tests run with `bun --conditions=browser test`. Native layout,
painting, dialogs and platform window behavior still require a display-backed host.

## Consume the SDK another way

- **Source instead of `dist`:** add the `solidGpuiSource()` plugin and run Bun with
  `--conditions=solid-gpui-source`; `bunfig.toml` cannot set custom conditions.
  Ordinary package use stays `dist`-based. See
  [source consumption](vite.md#consume-packages-from-source).
- **Rust owns Vite:** `solid_gpui::runtime::vite::Vite` starts this same
  configuration from a Rust process. See [Rust-owned Vite development](vite.md#rust-owned-vite-development).
- **One executable:** embedded Bun packaging is experimental. See
  [runtime strategy](runtime-strategy.md) and
  [embedded Bun static applications](distribution.md#embedded-bun-static-applications).

Repository contributors run the shared website instead:
`bun run website:native` (native), `bun run website:native:dev` (native hot
reload), or `bun run website` (browser). See the
[website README](../examples/website/README.md).
