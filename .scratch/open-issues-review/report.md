## #3 — transparency without background blur

Verdict: the reported Selection material and custom layer rewriting were still
present. The reporter's same-process Selection-to-Sidebar experiment is strong
evidence for material selection; the original visual symptom was not independently
reproduced here. A native implementation repair is now in the working tree.

Apple's [NSVisualEffectView contract](https://developer.apple.com/documentation/appkit/nsvisualeffectview)
says to choose material by intended use rather than apparent color, and explicitly
says not to override `draw` or `updateLayer`. Sidebar is a window-sidebar background;
Selection indicates selection. Materials and system preferences control the final
appearance, so a colorless, constant-strength blur is not a supported contract.

Implementation:

- Create an ordinary `NSVisualEffectView` in the existing background lifecycle.
- Set Sidebar, explicit BehindWindow blending and the existing Active state.
- Delete BlurredView registration, its updateLayer override and recursive private
  layer/filter mutation. No compatibility wrapper, OS-version branch, custom
  shader or polling path was added.
- Keep one content-sized, autoresizing effect behind the Metal view; switching
  away from Blurred removes it, and switching back creates a configured view.

Work/ownership: constant-size setup when enabling the effect; content-view
ownership releases it when removed. AppKit owns resizing, material composition
and accessibility adaptation. There is no GPUI per-frame material traversal.

Verification:

  `cargo clippy --locked -p solid-gpui --features test-support --test host_background_platform -- -D warnings`.
- Changed Rust files passed `rustfmt --check`; `git diff --check` passed.
- The real desktop `host_background_platform` test passed on macOS 27.0. It
  exercises initial creation, repeated enable, Opaque/Transparent removal,

- This is native lifecycle evidence, not a pixel-level compositor or human
