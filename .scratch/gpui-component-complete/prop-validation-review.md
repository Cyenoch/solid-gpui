# Pre-publication validation of numeric and collection properties

This review traced JavaScript properties in `primitives.rs`, `groups.rs`, `content.rs`, `extra_elements.rs`, and `table_elements.rs` to their actual vendor consumers. It identified five classes of issues: Rating/Pagination amplify small integer inputs into many native elements, Form/Field can create thousands of grid tracks, some pixel parameters accept negative values, and DescriptionItem spans can exceed actual columns. An unchecked integer type alone was not treated as a defect, and stateful NativeView components were outside scope.

Only this report changed. Independent temporary Taffy 0.13.0 layout probes ran without modifying repository tests or opening a native window. ## Concrete inputs requiring early rejection

### 1. P1 — Rating.max directly controls per-render element and closure counts

The unbounded `max: u32` enters `.max(max as usize)`. Rating renders `for ix in 1..=max`, creating Div/Icon elements and potentially mousemove/click listeners per item. The short valid native JSON/u32 input `max=4_294_967_295` attempts about 4.3 billion items. disabled=true still constructs them. [Adapter](/Users/jgbingzi/workspace/sp/solid-gpui/crates/solid-gpui/src/components/primitives.rs:297), [unbounded builder](/Users/jgbingzi/workspace/sp/solid-gpui/vendor/gpui-component/crates/component/src/rating.rs:67), [actual loop](/Users/jgbingzi/workspace/sp/solid-gpui/vendor/gpui-component/crates/component/src/rating.rs:149)

Minimal fix: decode max through a bounded value type at publication and reject values above a fixed `MAX_RATING_STARS`, initially perhaps 100. **100 is a proposed product limit; source evidence establishes only the need for a workload bound.** max=0 produces an empty control and needs no panic-prevention rejection. The value/max builders already clamp value>max, so it is not another out-of-bounds defect.

### 2. P1 — Pagination.visiblePages and totalPages have independent amplification paths

`currentPage/totalPages/visiblePages` are plain u32. Non-compact mode builds page_numbers: `total<=visible` allocates a complete `1..=total` Vec, and other branches generate ranges based on visible. Less obviously, visiblePages=5 does not make totalPages safe: opening each Ellipsis iterates its entire hidden range and creates one PopupMenuItem per page. `.max_h(240).scrollable(true)` limits the viewport, not construction. [Adapter](/Users/jgbingzi/workspace/sp/solid-gpui/crates/solid-gpui/src/components/primitives.rs:233), [page-item algorithm](/Users/jgbingzi/workspace/sp/solid-gpui/vendor/gpui-component/crates/base/src/pagination.rs:163), [non-compact entrypoint](/Users/jgbingzi/workspace/sp/solid-gpui/vendor/gpui-component/crates/component/src/pagination.rs:170), [full menu range](/Users/jgbingzi/workspace/sp/solid-gpui/vendor/gpui-component/crates/component/src/pagination.rs:218)

Triggers: `totalPages=visiblePages=4_294_967_295, compact=false` amplifies work on first render; `totalPages=4_294_967_295, visiblePages=5, compact=false` begins with a small page strip but amplifies on an ellipsis click. This risks excessive work/OOM; it is not mathematically infinite iteration.

Minimal fix: decoded-prop validation separately budgets effective page items and each ellipsis range in **non-compact** mode. Compute lengths with O(1) boundary formulas before allocation, never by constructing `.items()` and counting afterward. A sufficient initial contract is `visiblePages<=100 && totalPages<=1000`; these are proposed product limits. Supporting larger totals requires changing native menu rendering, outside this report. compact=true constructs only previous/next buttons and does not have this amplification. Native normalization already handles currentPage=0, totalPages=0, currentPage>total, and visiblePages<5; these are not new panic points.

### 3. P2 — Form.columns and Field grid properties can create thousands of tracks

Form.columns is u16 passed directly to `grid_cols`; Field.colSpan is u16 and colStart/colEnd are i16 passed directly into grid placement. Host style validation does not protect native DTO fields. [Form adapter](/Users/jgbingzi/workspace/sp/solid-gpui/crates/solid-gpui/src/components/groups.rs:261), [Field adapter](/Users/jgbingzi/workspace/sp/solid-gpui/crates/solid-gpui/src/components/groups.rs:276), [Form grid](/Users/jgbingzi/workspace/sp/solid-gpui/vendor/gpui-component/crates/component/src/form/form.rs:105), [Field placement](/Users/jgbingzi/workspace/sp/solid-gpui/vendor/gpui-component/crates/component/src/form/field.rs:271)

The pinned chain is GPUI 0.3.3 → Taffy 0.13.0. GPUI directly converts these values into repeat/GridPlacement. Taffy caps each grid direction at 10,000 tracks, so **maximum u16 input must not be reported as necessarily overflowing or looping forever**. A single numeric field can still create thousands of tracks: `columns=65535`, `colSpan=65535`, and `colStart=-32768/32767` all reach this path. [GPUI setters](/Users/jgbingzi/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/gpui-pre-0.3.3/src/styled.rs:752), [conversion](/Users/jgbingzi/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/gpui-pre-0.3.3/src/taffy.rs:452), [Taffy limit](/Users/jgbingzi/.cargo/registry/src/index.crates.io-1949cf8c6b5b557f/taffy-0.13.0/src/compute/grid/types/coordinates.rs:7)

An isolated 600×100 grid with one empty Field used the same GPUI-to-Taffy mapping. columns=65535 produced a zero-width field in about 5.3 ms; colSpan=65535 took about 7.0 ms; extreme positive/negative colStart took 4.4–4.7 ms and also produced zero-width fields. These are debug Taffy CPU probes, **not native presentation or performance acceptance**. They establish substantial layout-work amplification from small properties.

Minimal fix: use one small explicit grid budget for Form columns and Field spans/lines. Limiting parent columns alone still permits large implicit grids through child placement. An initial policy could use 64 columns, span<=64, and `abs(colStart/colEnd)<=65`. Convert positions to i32 before abs to avoid i16::MIN overflow. The 64-column budget is a proposal. Current Taffy safely normalizes zero columns/span/line; requiring nonzero values would tighten the domain contract, not fix an established panic. Negative line indices and reversed start/end are supported CSS behavior, not inherently invalid.

### 5. P2 — DescriptionItem.span exceeding actual columns creates an empty first row and invalid proportions

DescriptionList.columns is clamped to 1..10, while DescriptionItem.span remains unchanged. On an initial oversized span, group_item_rows creates an empty first row, then pushes another because `current_span+span>columns`. Cleanup removes trailing empty rows only, leaving the first empty row. Rendering directly uses `span/columns` as flex_basis: columns=1 with first span=2 gives an empty first row and 200% basis; span=65535 gives a 65,535-fold basis. [Adapter](/Users/jgbingzi/workspace/sp/solid-gpui/crates/solid-gpui/src/components/content.rs:102), [unchecked span](/Users/jgbingzi/workspace/sp/solid-gpui/vendor/gpui-component/crates/component/src/description_list.rs:121), [row grouping](/Users/jgbingzi/workspace/sp/solid-gpui/vendor/gpui-component/crates/component/src/description_list.rs:235), [basis](/Users/jgbingzi/workspace/sp/solid-gpui/vendor/gpui-component/crates/component/src/description_list.rs:330)

Minimal fix: ordinary Items require `1<=span<=effective_parent_columns`. span<=10 alone still fails with parent columns=1 and span=10. The separator=true branch ignores span, so that unused value is not an actual range defect. Standalone DescriptionItem is wrapped by DescriptionPart in a default three-column native DescriptionList; if this entrypoint remains supported, its effective maximum is 3. [Standalone entrypoint](/Users/jgbingzi/workspace/sp/solid-gpui/crates/solid-gpui/src/components/content.rs:14), [default columns](/Users/jgbingzi/workspace/sp/solid-gpui/vendor/gpui-component/crates/component/src/description_list.rs:144)

Candidate composition must compare parent columns with child span/separator; an independent u16 newtype is insufficient. Reuse native DTOs already decoded during candidate validation rather than building elements first. Existing validate_composition summaries contain only kind/type metadata; add explicit read-only child-prop access for this relationship instead of another renderer-wide traversal. span=0 does not stop the loop: it consumes no columns and yields zero basis, an invalid placeholder contract rather than an infinite loop.

## Minimal validation placement and executed evidence

Single-property workload/pixel rules belong in Rust Deserialize types, entering publication through ComponentDefinition::validate decoding. Pagination compact/count relationships and Description parent/child relationships need composition validation. Do not conceal invalid inputs with render-time clamping or panic catches. Snapshot/Patch candidate validation already precedes store replacement; preserve atomic rejection. [Decode gate](/Users/jgbingzi/workspace/sp/solid-gpui/crates/solid-gpui/src/native/component.rs:550)

Temporary Taffy probes used actual GPUI repeat/GridPlacement mappings for eight input classes: zero columns, span, and line; maximum columns/span; minimum/maximum i16 lines; and reversed line ranges. All returned normally without panic or a three-second timeout. The three zero cases produced normal 600 px fields; reversed lines 3→1 resolved to 400 px. This rules out claims that zero/negative lines necessarily crash. Temporary source/build directories were removed, and probes were not added to repository tests.

Retain only key implementation checks: oversized Rating, both non-compact Pagination amplification cases, extreme Form/Field grids, four negative-pixel fields, and Description parent/child span relationships reject before publication with old revisions/instances unchanged. Also retain accepted normal boundary values and compact mode with large totals. Do not duplicate each existing native builder clamp in new tests.
