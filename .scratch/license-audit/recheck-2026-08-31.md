# License terms determinability re-check

Date: 2026-08-31  
Scope: the pinned Zed checkout at `6805d952f9f3d702f760aa11b1547df8a625fa16`, its fetched `origin/main`, and the two remaining `gpui_shared_string`/`gpui_util` findings. This is read-only evidence; no vendored source or Cargo manifest was changed.

## Verdict

**DOWNGRADE the framing, but keep the publication STOP.** The absent `license` fields do not make the terms unknowable. Both crates carry an explicit `LICENSE-APACHE` file, implemented as a symlink to Zed's root `LICENSE-APACHE`; the control crate `gpui` carries the same per-crate file, with identical contents. The file states the Apache License, Version 2.0. Zed's README says its source is primarily GPL-3.0-or-later "with Apache-2.0 components where marked," and these crates are marked by those per-crate Apache files.

Therefore the narrow finding is **known Apache-2.0 text + missing Cargo metadata**, not unknown terms. The missing metadata still produces `cargo-deny`'s `no-license-field` warnings and should be fixed upstream (or otherwise represented in package metadata), and a release owner/legal reviewer must confirm that this Apache-2.0 marking governs the exact distributed crate/artifacts and satisfy notices and any other obligations. The independent `self_cell` choice and weak-copyleft/artifact review remain. This evidence does not authorize publication or remove the STOP.

| Crate | Files found | Link target / comparison |

No per-crate `LICENSE` or `LICENSE-MIT` file was found for these three crates. The root has `LICENSE-APACHE` and `LICENSE-GPL`; it has no file literally named `LICENSE`. The same symlinks are tracked in `origin/main` (`git ls-tree` mode `120000`), so this is not an artifact created only by the checkout tooling.

The license text is the same for all three per-crate links and the root file (`md5 776e07ed20b75b675553b3a113323c42`). Exact text from each linked file:

The `gpui` control manifest explicitly says `license = "Apache-2.0"` (`crates/gpui/Cargo.toml:9`), while the two target manifests have no `license` or `license-file` field (`gpui_shared_string/Cargo.toml:1-16`; `gpui_util/Cargo.toml:1-15`). The per-crate file evidence identifies the license text despite that metadata omission. It does not, by itself, replace a holder/legal confirmation of the intended package metadata and exact distribution treatment.

## Probe 2 — Zed repository policy

### Root files and policy

There is no root `LICENSE` file in this revision. The root license files are `LICENSE-APACHE` and `LICENSE-GPL`; no `LICENSE-AGPL` file was found. `CONTRIBUTING.md` contains contributor-process and CLA guidance but no crate-specific license map. Its exact relevant text is:

> `Additionally, contributors must sign our Contributor License Agreement (https://zed.dev/cla) before their contributions can be merged.` (`CONTRIBUTING.md:5-8`)

Zed's README provides the repository's explicit source policy:

> `Zed source code is licensed primarily under GPL-3.0-or-later, with Apache-2.0 components where marked.` (`README.md:30-32`)
>
> `License information for third party dependencies must be correctly provided for CI to pass.` (`README.md:34`)
>
> `We use [cargo-about](https://github.com/EmbarkStudios/cargo-about) to automatically comply with open source licenses.` (`README.md:36`)
>
> `Is it showing a "no license specified" error for a crate you've created? If so, add publish = false under [package] in your crate's Cargo.toml.` (`README.md:38`)
>
> `Is the error "failed to satisfy license requirements" for a dependency? If so, first determine what license the project has and whether this system is sufficient to comply with this license's requirements. If you're unsure, ask a lawyer.` (`README.md:39`)
>
> `Is cargo-about unable to find the license for a dependency? If so, add a clarification field at the end of script/licenses/zed-licenses.toml, as specified in the cargo-about book.` (`README.md:40`)

The root or `.config/` has no `deny.toml`. Zed instead has `script/licenses/zed-licenses.toml`, a cargo-about policy. Its exact allowlist begins:

> `accepted = [`
> `    "Apache-2.0",`
> `    "MIT",`

> `    "Apache-2.0 WITH LLVM-exception",`
> `    "MPL-2.0",`
> `    "BSD-3-Clause",`
> `    "BSD-2-Clause",`
> `    "ISC",`
> `    "CC0-1.0",`
> `    "NCSA",`
> `    "Unicode-3.0",`
> `    "OpenSSL",`
> `    "Zlib",`
> `    "BSL-1.0",`
> `    "bzip2-1.0.6",`
> `    "CDLA-Permissive-2.0",`
> `]`

The allowlist is a dependency-policy list, not a per-crate declaration, and contains no `gpui_shared_string` or `gpui_util` clarification. It corroborates that Apache-2.0 is an accepted Zed dependency license, while the README's “where marked” wording and the per-crate symlinks provide the crate-specific mark.

### Probe 2 conclusion

Zed's repository policy does not contain a separate deny configuration naming these two crates. It does, however, explicitly distinguish Apache components by marking and ships the exact Apache-2.0 text in the per-crate files. Combined with Probe 1, this is sufficient to identify the terms for this re-check; it is not a reason to infer a license for an unmarked crate.
